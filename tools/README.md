# Инструменты пакета

Основные генераторы и валидаторы используют стандартную библиотеку Python 3.10+. Браузерная проверка отдельно требует уже установленные Playwright/Chromium, независимое чтение экспортов — trimesh/numpy. Ничего не устанавливается автоматически. Сначала прочитать код. Скрипты не устанавливают Unity, Blender, MCP или Python, не обращаются к платным API и не содержат игровой runtime.

| Файл | Что делает | Что НЕ доказывает |
|---|---|---|
| `validate_pack.py --mode review` | Структура, ссылки данных, идентификаторы, зависимости, языки и фиксированный baseline | Что модели существуют или игра работает |
| `validate_pack.py --mode production` | Те же проверки + разрешение этапа разработки | Работоспособность будущей сборки |
| `validate_pack.py --mode release` | Те же проверки + все разрешения выпуска | Автоматическую юридическую или физическую безопасность |
| `check_gate.py review/preflight/install/develop/publish` | Проверка записанных явных разрешений | Не является ОС-песочницей и не удостоверяет личность подписанта |
| `build_reader.py` | Пересобирает reader, единый Markdown, PROGRESS и TRACEABILITY | Не утверждает изменённый дизайн |
| `make_review_bundle.py` | Собирает публичные текстовые исходники в один файл | Не включает личные фото/аудио и не повторяет готовый HTML |
| `make_manifest.py` | Обновляет SHA-256 манифест после проверенных изменений | Хеш не является оценкой качества |
| `verify_manifest.py` | Проверяет неизменность набора файлов и содержимого | Не проверяет код игры |
| `Inspect-Environment.ps1` | После P0-разрешения читает базовые характеристики Windows и пишет локальный отчёт | Не тестирует SDK и не запускался на Windows при создании этого пакета |

`--root` у Python-инструментов нужен для тестов и отдельной копии пакета. По умолчанию корень определяется относительно файла скрипта, не относительно рабочего каталога.

**Сначала проверить полученный манифест, затем редактировать.** После правок пересобрать производные документы, заново провести тесты, обновить отчёт и bundle, в конце — манифест. Нельзя «исправить» несовпадение хеша перезаписью манифеста без объяснения изменённых файлов.

Gate опирается на собственное состояние пакета и ссылки на явные указания владельца. Агенту запрещено самостоятельно создавать такие указания. Эти скрипты помогают дисциплине, но не заменяют настройки безопасности Codex, Windows и MCP.

Автообновление настроек Codex, `ExecutionPolicy Unrestricted`, выполнение удалённых install-строк и запуск `latest/main/beta` не предусмотрены. Отсутствующий инструмент — блокер, а не повод обходить утверждение.

## Новое в v3
- prepare_task.py — bounded context + SHA256, без API/автодействий.
- stage_unity_sources.py — dry-run и только явно разрешённый staging в новую Assets-папку, без .meta/overwrite.
- analyze_metrics.py — строгая normalized CSV schema, CPU/GPU отдельно, никаких выдуманных исходных данных.
- build_logic_lab.py — офлайн HTML из того же reference runtime.js, который тестирует Node.
- capabilities.py — безопасное наличие программ в PATH, не гарантия установки/совместимости.
- art_pipeline/generators/render_review.py — будущий локальный review-render без сохранения исходного .blend.

C# harness не использует NuGet test framework, но установленный .NET и его targeting packs всё равно нужны. Browser checks требуют Playwright/Chromium и не являются обязательной runtime-зависимостью продукта. Reference JS не включается вторым игровым движком в APK.


## v4 подготовительные инструменты
- `pbr_contract.py --out NEW_DIR`: численные PBR данные и маленькая RGBA fixture; не рендер.
- `intake_contract.py INPUT --out NEW_FILE`: неполные/полные исходники замеров с единицами и происхождением; не геометрическая приёмка.
- `verify_task_capsule.py CAPSULE_DIR`: точное сравнение TASK/manifest с текущим work order и исходниками; не авторизация.
- `validate_v4.py`: текущие решения, ссылки материалов, измерений и ограничений контекста.
Исторические журналы v3 находятся в reports/history/v3, не являются текущими engine proofs.

## Дополнения v4
`pbr_contract.py` создаёт проверяемый численный контракт материалов и маленькую PNG-пробу, не рендер. `intake_contract.py` проверяет входные замеры и явные оси, не заполняет пропуски. `prepare_task.py` и `verify_task_capsule.py` фиксируют work order, approvals и содержимое контекста; хеш не даёт разрешения запускать задачу. `validate_v4.py` проверяет новый набор договорённостей. Регрессии: `python -m unittest discover -s tests_v4 -v`.

## Сохраняемые инструменты окружения v6
- `pipeline_v6.py --dry-run`: только объявленные source-шаги, не редакторы.
- `build_space_v6.py` и `check_space_v6.py`: реальные иерархии/UV0/контакты/непрерывная 2D-проверка маршрута.
- `inspect_exports_v6.py`: независимый парсер при уже имеющихся trimesh/numpy; новая папка отчёта.
- `browser_v6_checks.py`: текущие сценарии диагностического стенда; `browser_checks.py` — совместимая точка входа к ним. `browser_v4_checks.py` сохранён как исторический тест, не текущий выпускной gate.
- `compare_vectors_v6.py`: сравнить реально полученные результаты JS и C#; не переименовывать JS-отчёт в C#.
- `import_space_snapshot_v6.py` и `render_space_views_v6.py`: только после отдельного разрешения на локальный Blender.

Тесты проверяют ограниченные контракты; статическая проверка профиля не доказывает готовность полной игры. Подробности исполнения и восстановления: `docs/process/PREPARATION_RUNNER_V6.md`.
